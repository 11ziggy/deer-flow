# DeerFlow 学习课程编写规范

本文件适用于 `learn/` 目录下的课程大纲、课程正文和学习产出。目标是把课程建设成一套**基于当前 DeerFlow 源码、可用于深入理解项目并准备工程面试**的材料，而不是宽泛的知识汇总或要求学习者从零重写 DeerFlow 的开发教程。

## 课程目标

完成课程后，学习者应能够：

1. 用一张图解释 DeerFlow 的整体架构和主要依赖方向；
2. 完整追踪一次用户请求从 Gateway、Run、Agent Runtime、Model/Tool、Checkpoint、Event/SSE 到结束状态的过程；
3. 解释关键机制解决的问题、工作方式、不变量、失败场景、边界、代价和替代方案；
4. 指出结论对应的真实入口、核心实现和测试，而不是只复述课程文字；
5. 区分 DeerFlow、LangChain、LangGraph、模型提供商以及学习者自己的工作；
6. 在面试中完成简短定义、完整讲解、代码定位和设计追问。

课程不要求学习者从零重新实现 DeerFlow。实践的作用是验证理解；大规模二次开发属于可选路径，不得作为理解课程的默认前提。

## 编写责任与规则优先级

**编写者负责取证，正文负责讲清，读者负责理解和判断。** 编写者必须先完成必要的源码、测试与版本核对，再把支撑核心结论的最小证据及其解释呈现在正文。不能把固定路径的查找、长文件的筛选或结论的提炼留给读者，作为理解课程的前提。读者自行定位源码可以用于可选验证或面试练习，但重复劳动本身不是学习成果。

当本规范的要求发生冲突时，按以下顺序取舍：

1. 事实准确、证据可靠；
2. 本课核心问题与范围边界清晰，核心阅读路径自洽；
3. 用少量必要代码和测试建立可复核的依据；
4. 章节形式、横切问题和面试题的覆盖完整度。

不得为了统一格式或展示源码覆盖面，牺牲前两项。课程结构由本课问题和证据类型决定；超出本课范围的证据应移到所属课程或可选深挖。

## 现有课程处理原则

- 生成、审查或修改任何课程前，必须先完整阅读 `learn/README.md`，确认该课在整体大纲中的阶段目标、前置课程、范围边界、课程产出和后续衔接；不得只根据单课文件或本规范推测课程定位。
- `lesson-01-*` 至 `lesson-04-*` 视为已经完成的历史课程。除非用户明确要求，否则不得重写、重排或为了统一格式而回填。
- ==新规范从第 5 课开始执行==,前面 4 课不是好的模板。
- 当前 30 课的阶段和主题顺序原则上保留。若需调整顺序或改变课程范围，必须先与用户讨论并获得明确确认。
- 不得因为发现早期课程存在问题就擅自修改文件。可以在后续课程开头用简短的“前置知识确认”补足必要概念，但不得重复整课。
- 在写入或大幅修改课程、大纲前，先向用户说明拟修改内容并获得明确授权。用户提出意见、判断或建议，不等于授权编辑文件。

## 唯一核心主线

所有课程都应能放回同一条请求主线：

```text
用户输入
  → Gateway 接收请求并创建 Run
  → Runtime 组装 Model、Prompt、Tool 和 Middleware
  → 模型产生文本或 Tool Call
  → Runtime 校验并执行工具
  → Message / ThreadState 更新并写入 Checkpoint
  → Event / SSE 把执行过程传给前端
  → Run 完成、失败、中断或恢复
  → Eval 判断任务是否真正完成
```

每课必须说明自己位于主线的哪一段，并只说明与本课机制直接相关的横切影响；不要求逐项展开以下所有问题：

- **可靠性**：超时、重试、幂等、并发、中断和恢复；
- **安全性**：身份、权限、输入校验、Sandbox 和外部数据信任；
- **可验证性**：日志、事件、Token、测试、评测和审计证据。

无法放回主线、也不服务于横切问题的内容，应标为可选背景，不得占据课程主体。

对后续课程机制，只交代本课必须知道的接口或边界，不提前讲其内部实现、专项故障、测试矩阵和完整恢复方案。

## 整体大纲要求

六个阶段应分别回答下面的问题：

| 阶段 | 核心问题 | 面试成果 |
| --- | --- | --- |
| 第 1～5 课 | 模型、工具和 Agent Loop 怎样工作？ | 能解释最小 Agent |
| 第 6～10 课 | 一次请求怎样穿过 DeerFlow？ | 能讲完整核心请求链 |
| 第 11～15 课 | Agent 怎样安全地获得行动能力？ | 能讲 Tool、Sandbox、Skill、MCP 和能力边界 |
| 第 16～20 课 | 复杂任务和长上下文怎样管理？ | 能讲委派、规划、摘要、记忆和 RAG |
| 第 21～25 课 | 系统怎样处理中断、重复和失败？ | 能讲运行时可靠性 |
| 第 26～30 课 | 怎样评测、部署并用于面试？ | 能完整陈述项目 |

从第 5 课开始，大纲中的每课至少声明：

1. **核心问题**：本课只围绕一个主要工程问题；
2. **主线位置**：本课位于完整请求链的哪里；
3. **必须掌握**：面试中需要真正解释的内容；
4. **暂时不讲**：用于控制边界和前后依赖；
5. **代码证据**：编写者已核对并在正文解释的少量入口、类型、调用路径和测试；
6. **面试验收**：学习者最终应该能够怎样表达和回答追问。

不得只用“学习内容、实践任务、课程产出”三个宽泛字段替代以上约束。

## 核心概念的讲解检查

对本课核心机制及必须深入掌握的概念，用下面的问题检查讲解是否足够。这不是固定写作顺序，也不要求逐项设节或让每个术语回答全部问题；只保留能帮助理解本课核心问题的项目：

1. **具体问题**：没有它时会出现什么需求缺口或故障；
2. **定义与位置**：它是什么，位于哪一层，上游和下游是谁；
3. **输入、输出与状态**：它读取什么、修改什么、产生什么；
4. **最小示例**：使用一条可跟踪的请求或状态变化说明；
5. **机制与不变量**：它怎样工作，哪些条件必须保持；
6. **边界与代价**：它解决什么、不解决什么，引入什么复杂度；
7. **失败与恢复**：本课涉及可靠性时，分析属于当前层次的失败场景及系统反应；
8. **代码与测试证据**：呈现并解释当前仓库中的必要实现和验证；
9. **学习要求**：明确必须掌握、只需知道和可以暂时跳过的内容。

不得用“为什么需要 X”作为一个尚未定义的 X 的开场。英文术语第一次出现时必须先给出中文含义，例如“未配对工具调用（dangling tool call）”。不得连续堆叠未解释的英文术语、缩写、中间件名称或类名。

非核心术语首次出现时，只给出足以继续阅读的简短定义和本课中的位置；完整机制留到它所属的课程。可以用同一案例串联几个必要问题，也可以用对比、状态图或故障推演建立因果链；不得机械重复同一结论。

尚未具备前置知识的实现只能标为“后续预告”，不能进入当前课程验收。预告应简短，不得用未来实现列表充当当前讲解。

## 事实可靠性与证据

课程是学习导航，不是项目实现的权威来源。事实判断遵循以下优先级：

```text
当前可运行代码与自动化测试
  > 当前仓库的 AGENTS.md、配置和架构文档
  > 可复现的运行日志、抓包和实验结果
  > 课程解释与总结
```

编写课程时必须遵守：

- 涉及模块代码前，先读取根 `AGENTS.md` 和该模块最近的 `AGENTS.md`；
- 用当前代码、测试和配置核对实现结论，不根据文件名或旧记忆猜测；
- 给出真实文件路径和稳定的符号名；行号只能作为辅助，不能代替符号定位；
- 对核心实现结论，在正文直接给出必要的短代码片段、调用关系或可复现行为，并紧接着解释它证明什么；标明真实路径与符号。伪代码必须明确标为示意，不能冒充仓库原文；不得大段复制源码；
- 文件和测试清单是复核入口，不是讲解的替代品。核心阅读不得以“请打开这些文件并自行寻找结论”为前提；源码查找任务应放在可选验证中，并说明预期发现；
- 说明框架自动完成、DeerFlow 自己实现和提供商负责的部分；
- 如果课程与代码、测试或运行结果冲突，以代码和证据为准，并报告冲突；
- 无法验证的内容必须标记为未验证、外部背景或推测，否则删除；
- 外部 API、SDK、模型能力等可能变化的事实，应核对目标版本的官方文档；
- 不得承诺后续课程一定详细覆盖大纲中没有明确列出的主题；
- 不得为了增加篇幅罗列生产概念、未来机制、常见误区或自测题。

## 每课结构选择

第 5 课及以后不使用统一章节模板。写作前先确定本课核心问题、主线位置、前置知识、必须掌握与暂时不讲的边界、验收方式和预计阅读负担；可以用导语、表格或简短列表交代，不要求固定元数据栏。正文的标题、顺序和篇幅由教学需要决定。

- **概念辨析课**可以从容易混淆的具体问题和最小对比入手，再解释边界与使用条件；
- **请求链路课**可以按一次请求的时间顺序组织，逐步呈现调用、状态和可观察结果；
- **机制分析课**可以围绕一个关键设计及其不变量，把必要的代码证据放在对应解释旁边；
- **可靠性专题课**可以从故障和状态变化切入，再分析防护、恢复与代价。

这些只是可选组织方式，不是新的分类模板。一课也可以组合几种方式，但必须保持一条清晰的论证主线。代码、测试、图、案例、面试回答和可选验证应放在最有助于理解的位置，不必各占一节；没有独立教学价值的部分应省略。凡是核心结论，都要在正文给出足以理解和复核的证据，不能靠读者另行查找。若完整故障处理属于后续课程，本课只交代当前边界。

## 内容分层与快速阅读

出现相应内容时，应让读者能区分：

- **核心内容**：仅阅读课程也必须理解，是面试验收范围；
- **代码深挖**：用于建立源码证据，选择少量关键路径；
- **可选验证**：用于验证理解，不要求从零实现；
- **扩展阅读**：与当前主线关系较弱，可暂时跳过。

核心阅读路径必须自洽。学习者跳过实验和扩展内容后，仍应能够理解本课的完整因果链并完成面试验收。

核心阅读不以打开仓库源码、运行程序或阅读另一份笔记为前提。代码深挖应与核心正文明确分开；每个要求读者打开的文件或测试都要说明它提供的独立学习收益，以及为什么正文中的证据还不足以完成该项验证。同一课只选择与核心问题直接相关的主实现路径；Studio、嵌入式客户端等替代接线方式，除非正是本课主题，否则只作可选对照。

## 面试验收标准

每课的验收围绕本课核心问题设计，不固定题型或数量。学习者至少应能够：

1. 用自己的话简洁说明本课核心问题与机制；
2. 连贯讲清问题、机制与边界，讲述顺序可以随主题变化；
3. 说明正文已呈现的关键证据支持什么结论，并指出本课范围边界。

若本课重点是调用链、状态变化、失败恢复或设计取舍，再分别要求画链路、分析故障或比较替代设计；不要为了凑齐题型引入后续课程内容。需要练习面试表达时，可以另设 30 秒或 3 分钟版本，但不要求课程正文设置对应栏目。

面试问题必须能从课程正文中找到依据，不得在课后突然考查正文没有讲解的概念。

## 实践要求

若本课安排实践，可以按下表选择合适层级；不要求每课都提供三层任务，也不得把从零开发作为默认要求：

| 层级 | 目的 | 要求 |
| --- | --- | --- |
| 快速验证 | 建立代码或运行证据 | 推荐，可在时间有限时跳过 |
| 局部实验 | 观察参数、状态或故障变化 | 可选 |
| 深入实践 | 二次开发、测试或贡献 | 完全可选 |

不得因为学习者没有完成深入实践，就判定其没有理解课程。理解程度应按本课验收目标判断，不把代码定位、故障分析或设计追问强加给与之无关的课。

## 防止内容膨胀

- 一课只保留一个核心问题，案例数量以讲清它所需的最少数量为准；
- 同一结论不得在目标、正文、误区、自测和总结中反复改写；
- 列表只能用于总结，不能代替因果讲解；
- 不得为了显得全面而提前罗列后续 Middleware、Guardrail、恢复或部署机制；
- 代码片段必须服务于具体问题，不得大段复制源码；
- “常见误区”和“自测”只在确有独立价值时保留；
- 总结不得加入正文未讲过的新信息；
- 固定栏目不是完成标准。内容能用一个案例和一张图说清楚时，不扩写成多个重复章节。

发布或交付一课前，编写者还必须完成以下学习负担检查：

1. 隐藏所有可选验证与扩展阅读、不打开任何源码，能否仅凭核心正文完成本课面试验收？
2. 核心部分要求打开的每个文件、测试或外部文档，是否真的不可由正文中的最小证据替代？若不能说明独立收益，就移入可选深挖或删除。
3. 是否把后续课程的内部符号、实现分支或故障方案带入本课？若有，只保留当前因果链所需的边界说明。
4. 核心阅读预计时间是否计入代码片段、图表和必须进行的跳转？若实际材料明显超过预算，先删减或后移内容，再调整时间估计。
